# 01: Database Access - SQLAlchemy or SQL?

Status

## Problem Statement

We use Python, Flask, and SQLite for our web application, a stack that fully covers the needs of the current project.

We need to decide on an approach for accessing the database within our application. The two main options are writing raw SQL queries directly, or using SQLAlchemy as an Object-Relational Mapping (ORM) layer. This decision affects the formality, readability, feasibility, and convenience of database CRUD (create, read, update, delete) operations, as well as how easily the codebase can evolve over time.

## Decision

We will use SQLAlchemy as our primary database access layer instead of raw SQL.

As the person primarily responsible for the database, I find SQLAlchemy easier to write and understand. Since I consider understandability more important for my team than e.g. raw performance, this informed the decision in favor of SQLAlchemy.

*Decision was taken by:* github.com/A-Ye311 (Angelina Ye)

## Regarded options

We regarded two alternative options:

+ Plain SQL
+ SQLAlchemy

| Criterion | Plain SQL | SQLAlchemy |
| --- | --- | --- |
| **Learnability** | ✔️ Team already knows SQL, no new concepts needed | ❌ Requires learning ORM concepts and SQLAlchemy |
| **Readability** | ❌ Logic mixed with raw query strings, harder to follow | ✔️ Queries expressed as Python objects, closer to the rest of the codebase |
| **Debugging** | ✔️ Easy to copy a query and run it directly against the DB | ❌ Generated SQL is hidden |
